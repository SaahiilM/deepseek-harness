## 13:50 - round 10: phone saw empty state - fence vs Host header

  3080, the same server the browser uses. The real bug: my gate forwarded the
  client's Host header verbatim (tailnet name:gate-port), and the harness

- Fix 1: gate rewrites Host to 127.0.0.1:<UPSTREAM_PORT> on both HTTP and WS
  upgrades (classic reverse-proxy semantics; transport-agnostic).
- Fix 2 (found via stray listeners): disable() dispatched async during
  applicationWillTerminate raced process exit - gate orphans accumulated
  across app restarts. Added disableNow() (queue.sync) for termination.

  session.list envelope through the gate; WS upgrade via tailnet addr opens
  with live frames; graceful quit leaves ZERO gate processes; 59/59 checks.
- Learned: reverse proxies must rewrite Host or loopback-fence designs will
  403 remote clients invisibly (static loads, API dies). ps eww env scraping

## 14:00 - round 11: stale-cookie shadowing killed QR re-pairing
- User report after app restarts: scanning fresh QR yields gate 401
  "paired device required". Root cause: cookies ignore ports, and every app
  launch re-keys PAIR_SECRET - so the phone's OLD cookie (same MagicDNS host)
  arrived with every request, and presentedSecret checked cookie BEFORE the
  URL pair code; the one-time exchange could never win on an already-paired
  device.
- Fix: presentedCandidates collects ALL credentials (bearer, cookie, pair
  path/query); hasValidPairCode OR hasValidSecret grants access; valid code
  still triggers cookie mint + URL strip. Stale cookies are simply ignored.
- Verified matrix on live tailnet gate: stale-cookie + valid code -> 302 +
  cookie; stale cookie alone -> 401; current secret -> API envelope 200;
  59/59 shell checks unaffected.
- Learned: any scheme where secrets rotate per launch under a stable host
  must evaluate explicit enrollment credentials ABOVE ambient ones, or
  re-enrollment is impossible.
